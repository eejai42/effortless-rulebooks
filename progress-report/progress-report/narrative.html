§ 1What this isPlain terms

First, what a rulebook is

This proposal rests on one unfamiliar idea, so it is worth thirty seconds before anything else. Everything that follows is a consequence of it.

Software is normally built by translating a specification into code. Someone writes down what the business needs — the rules, the permissions, the calculations — and then developers translate that document into an application. From that moment the document and the application begin to drift apart. The code becomes the real system; the specification becomes a description of what someone once intended. Every later change has to be made twice, and only one of the two is enforced.

A rulebook removes the translation step. The specification is written in a structured form that a machine can execute directly: every table, every field, every calculation, every permission, every business rule, stated once. The database, the security model and the documentation are then generated from it. There is no second copy to keep in sync, because the specification is not a description of the system — it is the system.

The conventional model

  • Specification, then code
  • The spec describes; the code decides
  • Rules are scattered across the application
  • Each feature must be reconciled with the last
  • Documentation drifts from behaviour
  • Permissions are checks a developer must remember
  • “Why does it show this number?” needs an engineer

The rulebook model

  • Specification as the system
  • The spec is executable; nothing overrides it
  • Rules live in one place, stated once
  • Features are added, not reconciled
  • Documentation is generated, so it cannot drift
  • Permissions are enforced by the database itself
  • “Why does it show this number?” is answered on screen

For this platform, that rulebook already exists. It holds 36 tables and 715 fields — 0 of them generated into the application and its security model, plus 36 that exist only to drive this proposal and the delivery report — covering the domain and the platform around it: every role, route, business rule, screen and acceptance criterion.

The consequence to hold on to

Because the specification executes, the usual gap between “what we agreed” and “what got built” does not open in the first place. That is what makes the rest of this document possible: the price, the schedule, the fixed bid, and the fact that the core of the platform is modelled before the contract is signed.

§ 2The claimCost curve

The two-hundredth feature does not cost dramatically more than the twelfth

In a conventional build, cost per feature climbs. Every new feature has to be reconciled against the ones already shipped — the code paths they share, the assumptions they made, the tests they broke. That compounding reconciliation is why software projects that start fast tend to finish slow.

Features here still interact; some are genuinely large, and a few will be hard for reasons that have nothing to do with architecture. What changes is that the most common category of cross-dependency is avoided rather than managed. The business logic lives in one declarative rulebook rather than spread across an application layer, so a new feature is largely a matter of adding to the model — not tracing what else in the codebase assumed the old behaviour.

This is not a claim about working harder, and it is not a claim that features are free or interchangeable. It is a claim about a different dependency structure, with a specific consequence: cost tends to scale roughly linearly with scope, instead of compounding.

§ 4CadenceTue / Fri

Two meetings a week, and a two-day turnaround

The cost curve is the commercial argument. The thing you will actually feel is the latency: how long it takes for something you said out loud to become something you can click.

We meet twice weekly, Tuesday and Friday. Features discussed on Tuesday are typically ready for testing — and often for deployment — by Friday. Not every feature, every time; some are genuinely large, and some wait on decisions or third-party access. But most changes land inside one two-day cycle, and that is the normal rhythm rather than the exceptional sprint.

This is downstream of the same mechanism. A rule change is one edit to the rulebook; the database, the API, the permission model and the plain-English documentation are regenerated together. There is no window in which the code says one thing and the spec says another, because the spec is what produced the code.

The practical effect on scope control is worth naming: because acceptance criteria are rows in the same rulebook, “is this done?” is answered against a written criterion with a name and a timestamp on it, twice a week — not in a disputed conversation at the end of a phase.

  2. Wed — ThuRulebook edit → regenerate → build the surfaces that need hand work.
  3. FridayMost of it is testable. Accept it, or feed it back into Tuesday.
§ 5ExplainabilityProvenance

Every number on every screen can show its work

Because the derivations are declared rather than implemented, the platform holds a complete dependency graph of how each value is computed. That graph is not a debugging tool for us — it is a product feature for your users.

Of the 715 fields in the model, 418 are computed rather than typed (58%). Each can be expanded in place to show the inputs that produced it, and each of those inputs expanded in turn, all the way down to values a person typed. For a platform whose purpose is producing auditable submissions, an interface that cannot be questioned is a liability. This one answers.

§ 6SecurityAudit posture

Each role gets its own database schema

Authorization here is not a middleware layer that every new endpoint must remember to call. It is the database's own access control, generated from the rulebook.

Each of the 0 roles receives its own Postgres schema exposing only the tables and columns that role may touch. Row-level security narrows that further to the specific rows — by construction rather than by a WHERE clause someone remembered to write. A forgotten application-layer authorization check cannot expose a field that the role's database schema does not contain.

The consequence worth stating plainly: this is a security model designed so that a tenant could, in principle, be handed a direct database connection and still see only their own data. That is a different category of model from one that depends on the application behaving correctly. Every tenant-scoped table carries a row predicate for every role, and the generator refuses to build if one is missing rather than defaulting to open access.

What this does to the audit

Most platforms answer an auditor with policy documents, screenshots and interviews. Here the controls are data, so the evidence is a query. Which roles can read personally identifiable fields? Which rows can this role see? When did this permission change, and who changed it? Each is answerable directly from the same rulebook that generated the enforcement. This makes the platform audit-ready by construction — it is not a certification, and we are not bidding one.

§ 7ExitNo lock-in

What you own, and what happens if we disappear

Everyone who has commissioned custom software has been on the wrong end of it: the vendor holds the only copy of how it works, and the only artifact that fully describes the system is source code you cannot read and did not write.

Our answer is structural rather than contractual. The specification is data. The business logic is data. The security model is data. The acceptance record is data. All of it exports — and the running system underneath is standard PostgreSQL, not a proprietary runtime.

The feasibility check that keeps this honest

Internally we do model effort — we would be reckless to commit to a date without testing whether it is achievable. Every phase carries a modelled effort and a capacity ratio against its committed duration. That instrument exists to keep our own promises honest, not to describe a staffing plan, which is why its outputs are not in the pricing table. The 0 external dependencies that no amount of engineering removes are modelled explicitly as roadblocks, and modelled concurrently — the schedule absorbs the worst single one, not their sum, because that is how waiting actually works.
